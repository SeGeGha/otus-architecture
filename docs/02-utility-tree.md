# Дерево полезности

## Как читать документ

- **Основа:** ISO/IEC 25010. В дерево взяты не все характеристики, а только те, что диктуют архитектурные решения для данной системы.
- **Структура:** `Полезность → атрибут качества → характеристика (ISO под-атрибут) → сценарий-лист`.
- **Сценарий:** источник → стимул → окружение → артефакт → реакция → **мера** (измеримый критерий).
- **Приоритет каждого листа** — пара `(Важность для бизнеса, Техническая сложность)` по шкале **H / M / L**. Пара `(H, H)` = «критично и нетривиально» → первоочередная архитектурная проработка.

Контекст и драйверы — в [README](../README.md): D1 — агрегация геоданных, D2 — офлайн-режим, D3 — аудит и откат, D4 — realtime-коллаборация.

## Само дерево

```
Полезность
├── Performance Efficiency — Производительность                          [D1, D4]
│   ├── Time behaviour
│   │   ├── S1. Загрузка маршрута с геоданными → ≤ 500 мс (p95) ........ (H, M)
│   │   └── S2. Правка участника → видна у остальных ≤ 300 мс (p95) .... (H, H)
│   └── Capacity
│       └── S3. 50 участников онлайн → latency ≤ 300 мс, 5xx ≤ 0.1% ...  (H, M)
├── Reliability / Availability — Доступность                             [D1, D2]
│   ├── Fault tolerance
│   │   └── S4. Провайдер геоданных недоступен → кеш + деградация ...... (H, M)
│   └── Availability
│       └── S5. Потеря сети → редактирование продолжается, sync ≤ 5 с .. (H, H)
├── Reliability / Recoverability — Восстанавливаемость                   [D3]
│   ├── Recoverability
│   │   └── S6. Откат маршрута к версии N → состояние восстановлено ≤ 3 с (H, M)
│   └── Integrity
│       └── S7. Операция с маршрутом → запись в append-only лог ≤ 1 с .. (H, L)
└── Consistency — Согласованность                                        [D4]
    └── Integrity
        └── S8. Два участника правят одну точку → авторезолв ≤ 300 мс .. (H, H)
```

## Сценарии

### S1. Загрузка маршрута с агрегированными геоданными — (H, M)

**Источник:** пользователь.  
**Стимул:** открывает страницу маршрута с 20–50 точками интереса.  
**Окружение:** штатная нагрузка, провайдеры доступны, большинство точек закешировано.  
**Артефакт:** Query BFF (агрегирует данные от нескольких гео-провайдеров).  
**Реакция:** BFF параллельно запрашивает данные по точкам, нормализует форматы и отдаёт единый ответ клиенту.

**Мера:** полная страница маршрута с геоданными загружается за ≤ 500 мс (p95) при маршруте до 50 точек; при кеш-хите (L1/L2) — ≤ 100 мс.

*Почему (H, M):* медленный рендер маршрута разрушает UX — карта с пустыми точками бессмысленна. Средняя сложность: параллельные запросы к провайдерам, многоуровневый кеш, нормализация разнородных форматов.

---

### S2. Синхронизация правки между участниками — (H, H)

**Источник:** участник А.  
**Стимул:** перемещает точку маршрута на карте.  
**Окружение:** 2–5 участников одновременно редактируют маршрут, штатная нагрузка сервера.  
**Артефакт:** Realtime BFF (WebSocket-сессии + CRDT-слой).  
**Реакция:** правка транслируется через Realtime BFF всем активным участникам; каждый клиент применяет дельту локально через CRDT-операцию.

**Мера:** изменение видно у остальных участников за ≤ 300 мс (p95) с момента подтверждения на клиенте А; при нагрузке до 1000 событий/сек latency не выходит за этот предел.

*Почему (H, H):* задержка > 1 с делает совместное редактирование бессмысленным — один участник «прыгает» по чужим изменениям с секундным лагом. Высокая сложность: WebSocket с горизонтальным масштабированием (shared pub/sub), CRDT merge на сервере и клиенте.

---

### S3. Realtime-слой под нагрузкой нескольких сессий — (H, M)

**Источник:** несколько групп пользователей.  
**Стимул:** 50 участников одновременно активно редактируют маршруты в разных сессиях.  
**Окружение:** пиковая нагрузка в пределах ожидаемых значений.  
**Артефакт:** Realtime BFF + shared pub/sub.  
**Реакция:** система продолжает обслуживать все сессии без деградации latency и без ошибок доставки.

**Мера:** latency синхронизации остаётся ≤ 300 мс (p95) при 50 одновременных активных участниках; доля ошибок 5xx — не более 0.1% запросов.

*Почему (H, M):* без горизонтального масштабирования realtime-слой станет узким местом при росте аудитории. Средняя сложность: shared pub/sub между узлами BFF, шардирование WebSocket-сессий.

---

### S4. Провайдер геоданных недоступен — (H, M)

**Источник:** внешний провайдер геоданных.  
**Стимул:** HTTP-ответ с ошибкой или таймаут.  
**Окружение:** штатный режим работы, пользователь открывает маршрут.  
**Артефакт:** BFF-слой агрегации геоданных.  
**Реакция:** BFF возвращает данные из кеша с пометкой «данные могут быть устаревшими»; остальные провайдеры опрашиваются в штатном режиме; circuit breaker изолирует отказавший источник.

**Мера:** страница маршрута открывается в 100% случаев при отказе любого одного провайдера; ответ из кеша приходит за ≤ 500 мс (p95); сбой одного провайдера не блокирует данные от других.

*Почему (H, M):* без изоляции отказов один нестабильный провайдер роняет всю страницу. Средняя сложность: circuit breaker, многоуровневый кеш и стратегия инвалидации.

---

### S5. Потеря сетевого соединения во время редактирования — (H, H)

**Источник:** сетевая инфраструктура / устройство пользователя.  
**Стимул:** обрыв интернет-соединения.  
**Окружение:** пользователь активно редактирует маршрут, в сессии есть несохранённые изменения.  
**Артефакт:** клиентское приложение (локальный Event Store на базе IndexedDB / SQLite).  
**Реакция:** приложение переходит в офлайн-режим без перезагрузки; новые изменения записываются в локальный лог событий; при восстановлении соединения клиент инициирует синхронизацию.

**Мера:** 100% локальных событий синхронизированы с сервером после восстановления сети; синхронизация начинается автоматически за ≤ 5 с после реконнекта; потерь данных нет.

*Почему (H, H):* без офлайн-режима продукт не выполняет ключевое обещание D2. Высокая сложность: локальный event store, стратегия слияния при реконнекте, обработка конфликтов «клиент vs сервер».

---

### S6. Откат маршрута к предыдущей версии — (H, M)

**Источник:** участник маршрута.  
**Стимул:** запрос «вернуть маршрут к версии на вчерашний вечер».  
**Окружение:** штатный режим, маршрут активно используется другими участниками.  
**Артефакт:** Event Store (append-only поток событий маршрута).  
**Реакция:** система воспроизводит поток событий до нужной временной метки, формирует состояние и возвращает его; операция записывается как новое событие (история не затирается).

**Мера:** откат к любой версии за ≤ 3 с при истории до 10 000 событий; 100% операций с маршрутом зафиксированы в логе; история неизменяема.

*Почему (H, M):* D3 — без полной истории откат невозможен в принципе. Средняя сложность: Event Sourcing + периодические снапшоты для ускорения восстановления при большом объёме истории.

---

### S7. Операция с маршрутом попадает в аудит-лог — (H, L)

**Источник:** участник маршрута.  
**Стимул:** любое изменение: добавление точки, переименование, удаление, откат.  
**Окружение:** штатный режим.  
**Артефакт:** Event Store.  
**Реакция:** событие записывается в append-only лог с атрибутами: автор, временная метка, тип операции, состояние до/после.

**Мера:** 100% операций с маршрутом фиксируются в логе; задержка между операцией и её записью — ≤ 1 с (p95); записанное событие не может быть изменено или удалено.

*Почему (H, L):* аудит — обязательное условие D3. Техническая сложность невысока: append-only запись обеспечивается самой природой Event Store, реализованного для S6.

---

### S8. Конфликт при одновременном редактировании одной точки — (H, H)

**Источник:** участники А и Б.  
**Стимул:** в промежутке < 500 мс А меняет название точки, Б — её координаты.  
**Окружение:** оба участника онлайн, оба работают с последней актуальной версией.  
**Артефакт:** CRDT-слой (Yjs / Automerge).  
**Реакция:** CRDT применяет обе операции независимо — название из операции А, координаты из операции Б; финальное состояние одинаково у всех участников без ручного вмешательства.

**Мера:** 100% конфликтов между неперекрывающимися атрибутами одной точки разрешаются автоматически; конвергенция (единое состояние у всех) достигается за ≤ 300 мс (p95); пользователю не показывается диалог ручного разрешения.

*Почему (H, H):* без авторезолвинга совместная работа требует ручного вмешательства и немедленно ломает UX. Высокая сложность: выбор CRDT-модели под геоданные, тестирование конкурентных сценариев на конвергентность.

## Приоритеты (свод)

Первоочередная архитектурная проработка — сценарии (H, H): они и критичны, и технически нетривиальны.

| Сценарий | Характеристика | Приоритет | Драйвер |
|---|---|---|---|
| S2. Задержка синхронизации ≤ 300 мс | Time behaviour | (H, H) | D4 |
| S5. Офлайн-режим + sync ≤ 5 с | Availability | (H, H) | D2 |
| S8. Авторезолвинг конфликтов ≤ 300 мс | Concurrent integrity | (H, H) | D4 |
| S1. Загрузка маршрута ≤ 500 мс | Time behaviour | (H, M) | D1 |
| S3. 50 участников без деградации | Capacity | (H, M) | D4 |
| S4. Деградация при отказе провайдера | Fault tolerance | (H, M) | D1 |
| S6. Откат к версии ≤ 3 с | Recoverability | (H, M) | D3 |
| S7. 100% операций в аудит-логе | Integrity | (H, L) | D3 |

Сценарии S2, S5, S8 — первоочередные кандидаты на архитектурную проработку. Именно из S2 и S8 вырастает ключевой компромисс — см. [`03-trade-offs.md`](03-trade-offs.md).
