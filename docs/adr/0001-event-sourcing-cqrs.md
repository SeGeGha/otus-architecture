# 0001. Event Sourcing + CQRS для маршрутов

- **Status:** Принято
- **Date:** 2026-08-19
- **Deciders:** Сергей

## Context

Маршрут — центральная сущность системы. Вокруг него сходятся три драйвера:

- **D3** — полный аудит, откат и восстановление: кто, когда и что изменил; откат к произвольной версии;
- **D4** — realtime-коллаборация: параллельные правки без блокировок;
- **D1 / производительность чтения** — загрузка маршрута с геоданными ≤ 500 мс (p95), сценарий [S1](../02-utility-tree.md).

Самый честный способ закрыть D3 — хранить не текущую строку «маршрут», а **поток событий**: *«участник А добавил точку»*, *«участник Б переименовал»*, *«участник А откатил»*. Но тогда каждое открытие страницы превращается в воспроизведение всей истории — при тысячах событий это не укладывается в S1 (загрузка маршрута ≤ 500 мс).

Что рассматривал:

1. **Классическая CRUD-модель.** Текущее состояние в одной таблице, история — отдельный audit-лог или вообще без него. Просто и быстро читается, но откат и полная восстанавливаемость — отдельные механизмы, легко потерять связность «что было → что стало». Против D3.
2. **Event Sourcing без отдельной read-модели.** Состояние = replay событий на каждый запрос. История полная (D3), но чтение дорогое — против S1.
3. **Event Sourcing + CQRS.** Append-only Event Store как источник истины; отдельная денормализованная read-модель для быстрого чтения; команда и запрос разведены по разным путям.

Развёрнутый компромисс — в [`../03-trade-offs.md`](../03-trade-offs.md).

## Decision

Беру вариант 3 — **Event Sourcing + CQRS**.

- **Command BFF** принимает команды (создать маршрут, добавить точку, откатить версию), пишет событие в **Event Store** (PostgreSQL, append-only) и публикует его в Kafka.
- **Projection Worker** (отдельный сервис) читает Kafka и обновляет **Read Model** — денормализованную проекцию текущего состояния.
- **Query BFF** читает маршруты из Read Model и не воспроизводит историю на каждый запрос.
- Откат — это **новое событие** в логе, а не затирание старых; восстановление версии — replay до нужной метки (при необходимости со снапшота).
- Живая коллаборация (D4) идёт **отдельным каналом** (Realtime BFF + CRDT + WebSocket) и не ждёт обновления Read Model.

## Consequences

**Что выигрываю.** Полная неизменяемая история и откат «из коробки» (D3, [S6](../02-utility-tree.md), [S7](../02-utility-tree.md)). Загрузка страницы маршрута укладывается в ≤ 500 мс без replay всей истории (S1). Команда и запрос масштабируются независимо. Realtime-правки (D4, [S2](../02-utility-tree.md)) не зависят от отставания проекции — пользователи видят изменения через WebSocket/CRDT.

**Чем плачу.** Eventual consistency: между записью события и обновлением Read Model допустимо отставание (ориентир ≤ 2 с). Нужны Kafka (или аналог), отдельный Projection Worker, отдельная read-база, логика проекций и снапшоты для ускорения восстановления. Отладка сложнее: Event Store и Read Model могут временно расходиться. Операционная нагрузка выше, чем у одной CRUD-таблицы.

**Что отверг.** CRUD с audit-логом — не даёт надёжного отката и восстанавливаемости на уровне источника истины (D3). Event Sourcing без CQRS — полная история, но чтение не держит S1. Обе крайности либо ломают аудит/откат, либо убивают скорость открытия маршрута.
