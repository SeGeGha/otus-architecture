# 0002. Модель рендеринга: CSR для редактора, ISR для публичной страницы маршрута

- **Status:** Принято
- **Date:** 2026-10-15
- **Deciders:** Сергей

## Context

Сейчас фронтенд — одно SPA на CDN с чистым клиентским рендерингом (см. [C4 Containers](../views/c4-container.md)). Для всех экранов это одна модель, хотя драйверы у экранов разные:

| Экран | Кто открывает | Что важно |
|---|---|---|
| **Редактор маршрута** | участник после входа | интерактивность и realtime (D4), офлайн (D2); SEO не нужен |
| **Публичная страница маршрута** | кто угодно — по ссылке из мессенджера, из поиска, часто с телефона | SEO и быстрый первый экран на слабой сети |
| **Панель модератора** | модератор после входа | как у редактора, но экранов мало и они меняются редко |

Публичной страницы нет среди драйверов D1–D4 в [README](../../README.md): она появилась вместе с публичными маршрутами и их модерацией в [ДЗ-3](../04-capabilities.md). Для фронтенда это отдельный драйвер, и он тянет в противоположную сторону от редактора: редактору нужен «толстый» клиент с офлайном, публичной странице — готовый HTML как можно раньше.

При этом содержимое публичной страницы меняется редко: маршрут публикуют, иногда правят, изредка откатывают или скрывают. Живых данных, которые надо показывать с точностью до секунды, на ней нет — живое редактирование видят только участники в редакторе.

Что рассматривал:

1. **Чистый CSR везде** — как сейчас. Просто и дёшево: только статика на CDN. Но публичная страница отдаёт пустую оболочку: поисковик видит её хуже, а человек с телефона ждёт, пока скачается бандл, сходит запрос в Query BFF и отрисуется маршрут.
2. **SSR везде.** Быстрый первый экран и SEO для всего, но за это Node-рантайм на каждый запрос и гидратация в редакторе — а редактору SEO не нужен, и его первый экран всё равно за логином.
3. **Гибрид: CSR для редактора + SSR для публичной страницы.** Закрывает SEO и первый экран, но держит живой рендер-сервер ради контента, который почти не меняется. TTFB растёт под нагрузкой, когда маршрут разлетается по ссылке.
4. **Гибрид: CSR для редактора + ISR для публичной страницы.** Публичная страница рендерится заранее в статический HTML, лежит на CDN и перегенерируется, когда маршрут меняется.

## Decision

Беру вариант 4.

**Обоснование:** редактор живёт за логином и требует интерактивности и офлайна (D4, D2), а публичную страницу открывают по ссылке с телефона, и ей нужны SEO и мгновенный первый экран — при этом она меняется редко, поэтому её дешевле отрендерить заранее, чем на каждый запрос.

**Публичная страница — ISR с перегенерацией по событиям:**

- новый контейнер **Public Page Renderer** внутри «Маршрутов» слушает события маршрута, читает Read Model и публикует HTML на CDN;
- маршрут опубликован → страница генерируется;
- маршрут откачен к версии → перегенерируется;
- маршрут снят с публикации (в том числе после `RouteHidden` от Модерации) → страница **сразу** удаляется с CDN, без ожидания TTL;
- правки опубликованного маршрута → перегенерация не чаще раза в несколько минут: публичная страница — «официальное» состояние, ей не нужна живость редактора.

Первый экран публичной страницы — название, описание и список точек: обычный HTML и текст, который сразу становится LCP-элементом. Карта на первом экране — плейсхолдер; интерактивная карта догружается.

**Редактор и панель модератора остаются CSR** — то же SPA на CDN, как сейчас.

**Code splitting — две точки:**

1. **Картографический движок** (Mapbox GL JS — самый тяжёлый модуль фронтенда) — отдельный чанк. На публичной странице грузится, когда карта попадает в видимую область или по нажатию; в редакторе — после первой отрисовки списка точек.
2. **Ядро редактора** — CRDT (Yjs), WebSocket-клиент и офлайн-слой на IndexedDB — отдельный чанк маршрута `/routes/:id/edit`. Тот, кто только смотрит маршрут, его не скачивает. Панель модератора — тоже отдельный чанк по своему маршруту.

**Ожидаемый эффект** — направление и порядок величины, на среднем мобильном устройстве и 4G:

| Экран | TTFB | LCP |
|---|---|---|
| Публичная страница | остаётся ~100 мс: и сейчас, и после ответ идёт с CDN, но теперь в HTML уже есть содержимое | с ~3–4 с до ~1,5 с: не ждём бандл и запрос к Query BFF, LCP — текст из готового HTML |
| Редактор | без изменений, ~100 мс: оболочка SPA с CDN | с ~4 с до ~2–2,5 с: карта и CRDT больше не блокируют первую отрисовку списка точек |

TTFB здесь — время до первого байта HTML с CDN; это не то же самое, что ответ Query BFF ≤ 500 мс из [S1](../02-utility-tree.md). LCP при этом не может быть меньше TTFB, поэтому для публичной страницы главное — что HTML приходит с CDN, а не из рендер-сервера.

## Consequences

**Что выигрываю.** Публичная страница индексируется и открывается с первым экраном почти сразу, даже на слабой сети. В горячем пути публичной страницы нет живого сервера: всплеск переходов по ссылке принимает CDN. Редактор остаётся простым CSR с офлайном — никакой гидратации и рассинхронизации серверного и клиентского HTML там, где важнее всего интерактивность. Скрытый модератором маршрут исчезает с CDN по событию, а не «когда истечёт кеш».

**Чем плачу.**

- Новый контейнер Public Page Renderer и работа с CDN: публикация HTML и принудительный сброс. Сброс — критичная операция: если он не сработает, скрытый маршрут останется доступным. Поэтому, кроме сброса по событию, у страниц короткий TTL как страховка.
- Публичная страница отстаёт от правок на минуты — это сознательно, но участник, который только что поправил маршрут и открыл публичную ссылку, увидит старую версию.
- Две модели рендеринга: компоненты, которые нужны и публичной странице, и SPA (карточка точки, список), должны рендериться и при сборке, и в браузере.
- Если рендер упал или страница ещё не сгенерирована, CDN должен отдать оболочку SPA, и страница откроется по-старому, через CSR. Это деградация, а не ошибка, но её надо настроить.

**Что не решено.** [Hotspot про шаринг-ссылки](../07-event-storming.md#что-видно-на-доске) остаётся открытым: публичная страница — только для опубликованных маршрутов, а приватный просмотр по шаринг-ссылке идёт через SPA и проверку в Доступе, и о скрытии маршрута Доступ по-прежнему не знает.

**Что отверг.** Чистый CSR — пустая оболочка вместо первого экрана и слабое SEO для единственного экрана, где они важны. SSR везде — Node-рантайм и гидратация ради экранов за логином, которым SEO не нужен. SSR только для публичной страницы — живой рендер-сервер ради контента, который меняется раз в минуты, и растущий под нагрузкой TTFB.
