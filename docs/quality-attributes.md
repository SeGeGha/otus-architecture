# Атрибуты качества

## От драйверов к атрибутам

Драйверы сервиса:

- **D1** — агрегация геоданных из нескольких внешних провайдеров с разными протоколами и SLA;
- **D2** — офлайн-режим: пользователь редактирует маршрут без сети, изменения синхронизируются при реконнекте;
- **D3** — полный аудит, откат и восстановление состояния маршрута;
- **D4** — совместное редактирование маршрута в реальном времени без блокировок.

Из них вырастают четыре приоритетных атрибута. Все четыре — runtime: их наблюдает пользователь, а не только команда разработки.

| Атрибут | Тип | Где в ISO 25010 | Какой драйвер закрывает |
|---|---|---|---|
| Производительность | runtime | Performance Efficiency → Time behaviour, Capacity | D1, D4 |
| Доступность / отказоустойчивость | runtime | Reliability → Availability, Fault tolerance | D1, D2 |
| Надёжность / восстанавливаемость | runtime | Reliability → Recoverability | D3 |
| Согласованность | runtime | нет прямого аналога в ISO 25010; ближайшее — Reliability → Faultlessness | D3, D4 |

У «Производительности» два отдельных проявления с разными архитектурными следствиями:

- **BFF/агрегация (D1)**: пользователь открывает маршрут — нужно параллельно опросить несколько провайдеров и отдать результат за ≤ 500 мс. Это задача кеширования, параллелизации запросов и нормализации форматов.
- **Realtime-синхронизация (D4)**: правка одного участника должна дойти до остальных за ≤ 300 мс. Это уже задача WebSocket-инфраструктуры, CRDT-слоя и горизонтального масштабирования realtime-узлов.

**«Согласованность»** не входит в ISO 25010 как самостоятельная характеристика — стандарт не выделяет distributed consistency в отдельную категорию. Ближайшее по духу: `Reliability → Faultlessness` («система даёт корректный результат при штатной эксплуатации»), но это натяжка: ISO имел в виду единую систему, а не конкурентный доступ нескольких узлов. Я выношу «Согласованность» отдельным атрибутом потому, что она диктует принципиально другие архитектурные решения — CRDT и CQRS-проекцию, — которые не пересекаются с тактиками Fault tolerance или Recoverability. В дереве полезности она тоже стоит отдельной ветвью по той же причине.

Dev-атрибуты (модифицируемость, тестируемость) решил не выносить в приоритет.

## Чем закрываю каждый атрибут

- **Производительность** — два разных проявления одного атрибута, каждое со своей тактикой:
  - *Агрегация геоданных (D1):* параллельные запросы к провайдерам из одного BFF-обработчика; многоуровневый кеш (L1 in-memory → L2 Redis → L3 CDN) с TTL под каждый тип данных — координаты POI кешируются долго, рейтинги — коротко.
  - *Realtime-синхронизация (D4):* WebSocket вместо polling'а убирает лишний round-trip; shared pub/sub (Redis / Kafka) позволяет горизонтально масштабировать Realtime BFF; идемпотентность CRDT-операций делает ретраи безопасными.

- **Доступность / отказоустойчивость**:
  - *Circuit breaker на каждый внешний провайдер* — если провайдер начинает отвечать с ошибками или таймаутами, схема автоматически «размыкает цепь» и перестаёт его опрашивать на фиксированный интервал. Это предотвращает накопление зависших соединений и блокировку BFF в ожидании недоступного источника.
  - *Graceful degradation* — вместо того чтобы вернуть пользователю ошибку при отказе провайдера, BFF отдаёт данные из кеша с пометкой «данные могут быть устаревшими». Маршрут открывается, остальные провайдеры работают в штатном режиме, сбой одного изолирован.
  - *Локальный Event Store на клиенте* — при потере сети приложение переходит в офлайн-режим: новые правки пишутся в локальное хранилище (IndexedDB / SQLite), а не теряются. При восстановлении соединения клиент сбрасывает накопленные события на сервер.

- **Надёжность / восстанавливаемость**:
  - *Append-only Event Store* — каждое изменение маршрута записывается как новое событие, уже записанное не редактируется и не удаляется. Это исключает случайную потерю истории при обновлении или баге в коде.
  - *Периодические снапшоты* — при большом количестве событий воспроизводить всю историю с нуля медленно. Снапшот фиксирует состояние маршрута на определённый момент: восстановление начинается с ближайшего снапшота, а не с первого события.
  - *Откат как новое событие* — операция «вернуть к версии N» не затирает последующие изменения, а дописывает в лог событие «откат». История остаётся полной: видно, что был откат, когда и кем инициирован.

- **Согласованность**:
  - *CRDT-алгоритмы (Yjs / Automerge)* — правки разных участников математически сливаются без центрального арбитра. Если два человека одновременно изменили разные поля одной точки, оба изменения применяются независимо и дают одинаковый результат у всех участников, независимо от порядка получения.
  - *CQRS-проекция (read-модель)* — запись идёт в Event Store, а чтение обслуживает отдельная денормализованная проекция. Это позволяет читать текущее состояние маршрута за ≤ 500 мс, не воспроизводя всю историю событий при каждом запросе. Цена — допустимое отставание проекции от потока событий ≤ 2 с.
